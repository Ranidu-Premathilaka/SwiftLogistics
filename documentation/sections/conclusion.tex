\section{Conclusion}
\label{sec:conclusion}

\subsection{Summary of Solution}

The SwiftTrack integration platform is realised as an event-driven microservices architecture
comprising thirteen Docker containers coordinated via a single RabbitMQ topic exchange
(\texttt{swift\_logistics}), with Node.js services, shared PostgreSQL databases, and Docker
Compose orchestration. Three dedicated adapter containers bridge the heterogeneous legacy
systems---CMS (SOAP), ROS (REST), and WMS (proprietary TCP/IP)---without coupling any
application service to a protocol-specific dependency (see Section~\ref{sec:architecture}).

The architecture addresses each core requirement through distinct mechanisms:
asynchronous durable queues absorb peak order volumes without blocking the client;
the Notify Service delivers real-time updates via WebSocket push with offline persistence
for disconnected clients; the choreography-based Saga pattern handles distributed
transactions with WMS stock release as the compensating action on payment failure;
and the API Gateway enforces JWT authentication at the network boundary before any
request reaches a business service.

A functional prototype demonstrates all core flows---order submission, delivery lifecycle,
and real-time notifications---across seven integration test scenarios
(see Section~\ref{sec:prototype}). The client-facing web portal, TLS termination,
and production secrets management are deferred to future work;
the platform is otherwise complete and test-driven.

\subsection{Achievements}

\begin{itemize}
  \item Designed and documented a complete event-driven microservices architecture
        addressing all six challenges identified in the assignment brief
        (Section~\ref{sec:challenges}).
  \item Evaluated two alternative architectures (SOA/ESB and Three-Tier Monolith)
        with a comparative analysis justifying the chosen approach
        (Section~\ref{sec:alternatives}).
  \item Implemented a functional prototype with thirteen Docker containers, seven
        integration test scenarios, and no external paid service dependencies.
  \item Implemented the choreography-based Saga pattern with a complete compensation
        flow: WMS stock is released automatically when payment fails.
  \item Implemented offline notification persistence with automatic flush on
        WebSocket reconnect, satisfying the real-time tracking requirement for
        intermittently connected clients.
  \item Identified and documented all production-readiness gaps---TLS, Dead Letter
        Exchange, RBAC refinement, and secrets management---providing a clear path
        to deployment (Section~\ref{subsec:future_work}).
\end{itemize}

\subsection{Lessons Learned}

\begin{itemize}
  \item Choreography-based sagas eliminate the orchestrator bottleneck but require
        persistent saga state. The prototype stores \texttt{pendingPayments} in a
        JavaScript \texttt{Map}; any container restart loses in-flight transactions.
        A production system must persist this state to a database before the first
        event is published.
  \item The \texttt{PubSub} utility's auto-reconnect and subscriber-restore logic
        (\texttt{source-code/services/utility/pubsub.js}) proved essential during
        development: transient RabbitMQ restarts recovered automatically without
        manual service intervention.
  \item Standardising on Node.js across all thirteen services reduced integration
        friction through shared utility modules and a single runtime to maintain,
        at the cost of losing language-specific library ecosystems for individual services.
  \item Durable queues and manual consumer ACKs must be designed in from the
        start. Retrofitting delivery guarantees into a running distributed system
        requires coordinated redeployment of every consumer, which is far more
        disruptive than building them in upfront.
\end{itemize}

\subsection{Future Enhancements}
\label{subsec:future_work}

\subsubsection{Short-Term (Prototype to MVP)}
\begin{itemize}
  \item Build the SwiftTrack customer web portal (React or Vue SPA) and driver
        mobile application (React Native or Flutter) against the existing REST API.
  \item Add TLS termination via Nginx or Traefik in front of the API Gateway
        using Let's Encrypt certificates.
  \item Implement the Dead Letter Exchange and configurable retry policies
        designed in Section~\ref{sec:architectural_patterns}.
  \item Persist Saga state (\texttt{pendingPayments} Map) to PostgreSQL to
        survive container restarts.
  \item Replace the dummy payment processor with a real provider (PayHere or Stripe).
\end{itemize}

\subsubsection{Medium-Term (Operational Maturity)}
\begin{itemize}
  \item Migrate from Docker Compose to Kubernetes with a Helm chart and add
        Horizontal Pod Autoscaler on the Order, Notify, and Delivery services.
  \item Deploy a RabbitMQ cluster with mirrored queues for broker high availability.
  \item Separate shared PostgreSQL instances into per-service databases to enforce
        strict data isolation between microservices.
  \item Centralise logging with the ELK stack, add distributed tracing (Jaeger),
        and expose metrics via Prometheus and Grafana.
  \item Add rate limiting and a Web Application Firewall at the API Gateway layer.
\end{itemize}

\subsubsection{Long-Term (Business Extensions)}
\begin{itemize}
  \item Add GPS-based real-time driver location streaming using MQTT or WebRTC.
  \item Replace the mock ROS with a machine learning-assisted route optimisation
        engine while keeping the adapter interface unchanged.
  \item Extend to a multi-tenant architecture to white-label SwiftTrack for
        partner logistics firms.
  \item Build a business intelligence dashboard tracking order volumes, delivery
        KPIs, and SLA compliance.
  \item Integrate with external logistics networks such as Sri Lanka Post.
\end{itemize}

\subsection{Production Readiness Roadmap}

The following steps are required before the platform is suitable for production traffic,
ordered by dependency:

\begin{enumerate}
  \item \textbf{Security hardening}: TLS end-to-end, Docker secrets or Vault for
        credentials, and mTLS between internal services.
  \item \textbf{Saga durability}: persist Saga state (\texttt{pendingPayments})
        to PostgreSQL before any payment events are published.
  \item \textbf{Message resilience}: deploy the Dead Letter Exchange and configure
        retry policies for all consumer queues.
  \item \textbf{UI development}: build the customer web portal and driver
        mobile application.
  \item \textbf{Real payment integration}: replace the dummy processor with
        PayHere or Stripe.
  \item \textbf{Database separation}: migrate to per-service PostgreSQL instances.
  \item \textbf{Container orchestration}: migrate Docker Compose to Kubernetes
        with autoscaling policies.
  \item \textbf{Observability}: centralised logging (ELK), distributed tracing
        (Jaeger), and metrics (Prometheus/Grafana).
  \item \textbf{Load and penetration testing}: validate throughput targets and
        security posture before public launch.
\end{enumerate}

\subsection{Final Remarks}

The event-driven microservices architecture described in this report provides Swift
Logistics with a technically sound foundation that can scale with order volumes and
client growth without requiring a re-architecture. Each service has a single
responsibility and communicates exclusively through the message broker, meaning
individual services can be scaled, replaced, or redeployed independently.

The deliberate choice of open-source technologies---Node.js, RabbitMQ, PostgreSQL,
and Docker---eliminates vendor lock-in and keeps operational costs predictable. The
modular adapter design is particularly significant for long-term maintainability:
when a legacy system is eventually replaced or upgraded, only its single adapter
container needs to change; no application service is affected. This property makes
the platform a stable integration layer for the business regardless of how the
underlying technology landscape evolves.
