\subsubsection{User Story 2: Order Submission}

\paragraph{Description}
As a client, I want to submit a new delivery order so that my package can be picked up and delivered to the destination.

\paragraph{Actors}
\begin{itemize}
    \item Client
    \item API Gateway
    \item Order Service
    \item WMS Service
\end{itemize}

\paragraph{Sequence Diagram}

\paragraph{Business Details}
The order workflow is divided into three stages.
First, the client browses inventory; the system queries the WMS and returns the current stock list in real time via WebSocket.
Second, the client creates an order with a chosen item list; the system registers the order in the CMS legacy system and creates a payment intent, returning a clientSecret to the client via WebSocket.
Third, the client confirms the order using the clientSecret as the payment token; the system updates the CMS order status, reserves stock in WMS, and charges payment in sequence.
If all steps succeed the order is marked pending delivery the client is notified; on payment decline or insufficient stock, compensating events roll back the reservation and the client is notified of the specific failure.

\paragraph{Implementation Details}
Inventory browsing is a GET /items request; the Items Service queues a wms.items.request AMQP event to the WMS adapter, which calls the WMS legacy HTTP API, and the result is pushed to the client via WebSocket as items\_response.
Order creation is a POST /order \{itemList\}; the Order Service publishes cms.order.create to the CMS adapter (SOAP CreateOrder), which generates an orderId. The CMS adapter then publishes to the Payment Service, which calls dummyCreatePaymentIntent and notifies the client via WebSocket with payment\_intent\_created \{orderId, clientSecret\}.
Order confirmation is a PATCH /order \{orderId, status: order\_confirmed, data: \{paymentToken, itemList\}\}. Using the Saga (choreography) pattern, the Order Service coordinates: a CMS status update via AMQP, a WMS stock reservation (POST /api/wms/reserve), and a payment charge. A successful charge pushes payment\_completed to the client; stock or payment failure triggers compensating release events and pushes the appropriate failure event.
