%% GUIDE ─ Conceptual Architecture
%% ─────────────────────────────────────────────────────────────────────────────
%% Describe the five conceptual layers visible in the diagram:
%%
%%  1. CLIENT LAYER
%%     - SwiftTrack web portal (browser client)
%%     - Driver mobile application
%%     Both communicate with the platform exclusively through the API Gateway
%%     over HTTPS (HTTP in the prototype) and WebSocket.
%%
%%  2. API GATEWAY LAYER
%%     - Single external entry point.
%%     - Performs JWT verification before forwarding any request.
%%     - Routes on URL prefix: /auth → Auth Service, /order → Order Service,
%%       /items → Items Service, /deliveries → Delivery Service,

%%     - Injects x-username and x-role headers into forwarded requests.
%%     - Source: source-code/services/api-gateway/index.js
%%
%%  3. APPLICATION SERVICE LAYER  (internal, reachable only via API Gateway)
%%     a. Auth Service     – user registration / login / JWT refresh / logout
%%     b. Order Service    – HTTP façade + orchestrator for the order workflow
%%     c. Items Service    – proxy from HTTP to WMS via async RabbitMQ RPC
%%     d. Delivery Service – driver delivery assignment + real-time route push
%%     e. Payment Service  – pure event consumer/publisher (no HTTP server)
%%     f. Route Service    – pure event consumer/publisher; builds ROS call
%%     g. Notify Service   – WebSocket server + offline notification store
%%
%%  4. MESSAGE BROKER
%%     - RabbitMQ single topic exchange : "swift_logistics"  (durable)
%%     - All inter-service async communication flows through here.
%%     - Consumers use durable queues bound to routing key patterns.
%%     - Pattern: <system>.<entity>.<action>  e.g. "cms.order.create"
%%
%%  5. ADAPTER + LEGACY SYSTEM LAYER
%%     a. CMS (cms-service container) — SOAP mock + CMSAdapter
%%        · Legacy: Node SOAP server exposing CreateOrder,
%%          UpdateOrderStatus, GetOrdersByUser, GetNextPendingDelivery
%%        · Adapter: subscribes to cms.* keys, calls SOAP, re-publishes
%%     b. ROS (ros-service container) — HTTP REST mock + ROSAdapter
%%        · Legacy: Express server at /api/ros/optimize-route
%%        · Adapter: subscribes to ros.route.optimize / ros.delivery.optimize
%%     c. WMS (wms-service container) — HTTP REST mock + WMSAdapter
%%        · Legacy: Express server at /api/wms/items, /reserve, /release
%%        · Adapter: subscribes to wms.items.request, order.confirmed,
%%          wms.order.release, wms.delivery.update_status
%%
%%  DATA LAYER (crosses layers 3 and 5)
%%     - Single PostgreSQL 16 instance shared by Auth, CMS, and Notify
%%       services in the prototype.
%%     - Auth:   users, refresh_tokens tables  (auth.sql)
%%     - CMS:    orders table with JSONB item list  (cms.sql)
%%     - Notify: pending_notifications table  (notify.sql)

\subsubsection{API Gateway}
%% GUIDE:
%%  - Implemented in: source-code/services/api-gateway/index.js
%%  - Technology: Node.js built-in http module + http-proxy library.
%%  - Three responsibilities:
%%     1. Authentication enforcement: validateToken() verifies HS256 JWT
%%        using jsonwebtoken; rejects with 401 if missing, malformed, or expired.
%%     2. Identity injection: injects x-username and x-role headers into every
%%        forwarded request so downstream services trust the identity without
%%        re-verifying the token.
%%     3. Routing: resolveTarget() strips the service prefix from the URL and
%%        forwards to the correct internal container using the serviceMap in config.js.
%%        Routes: /auth → auth-service:3000, /order → order-service:3000,
%%                /items → items-service:3000, /deliveries → delivery-service:3000,
%%                /notify → notify-service:3000.
%%  - WebSocket upgrades are also proxied via proxy.ws() in the 'upgrade' event handler.
%%  - Only container with a host-exposed port (8081).
%%  Source: source-code/services/api-gateway/index.js + config.js

%% GUIDE:
%%  - Implemented in: source-code/services/auth-service/index.js

\subsection{Rationale for Final Architecture}
\label{subsec:rationale}

%% GUIDE ─ Rationale
%% ─────────────────────────────────────────────────────────────────────────
%%  Explain WHY event-driven microservices was chosen over the two alternatives
%%  (cross-reference §\ref{sec:alternatives}). Cover four dimensions:
%%
%%  1. HETEROGENEOUS INTEGRATION
%%     Each legacy system (CMS SOAP, ROS REST, WMS proprietary TCP/IP) is
%%     isolated behind its own adapter container. Protocol translation is
%%     encapsulated within the adapter; no other service ever knows or cares
%%     what protocol the CMS uses.
%%
%%  2. ASYNCHRONOUS HIGH-VOLUME PROCESSING
%%     RabbitMQ's durable queues decouple order receipt from backend processing.
%%     The Order Service can acknowledge the client immediately (HTTP 200) and
%%     publish to the exchange. Backend adapters process from their queues at
%%     their own pace, enabling burst absorption during Avurudu/Black Friday sales
%%     without blocking the client portal.
%%
%%  3. RESILIENCE AND GUARANTEED DELIVERY
%%     Durable queues with persistent messages mean that if the CMS adapter
%%     restarts mid-processing, the message is redelivered automatically because
%%     ack is only sent after successful processing (manual ack in pubsub.js).
%%     restart: unless-stopped provides container-level self-healing.
%%
%%  4. INDEPENDENT SCALABILITY
%%     Each container is independently deployable and scalable. In a production
%%     Kubernetes deployment, notify and order services can be scaled out during
%%     peak hours without touching the auth or payment services.
%%
%%  TRADE-OFFS
%%  - Higher initial complexity than a three-tier approach: 13 containers,
%%    distributed tracing across async flows, eventual consistency rather than
%%    immediate consistency.
%%  - Accepted trade-off: the operational benefits at scale outweigh the
%%    additional setup cost, especially as the team has unified on JavaScript/Node.js,
%%    minimising the polyglot complexity that often accompanies microservices.
%% ─────────────────────────────────────────────────────────────────────────
