\section{Proposed Architecture}
\label{sec:architecture}

The SwiftTrack platform is implemented as an event-driven microservices architecture. Thirteen Docker containers communicate asynchronously through a single RabbitMQ topic exchange named \texttt{swift\_logistics}. All external traffic enters through an API Gateway; no internal service is reachable from outside the Docker network.

\subsection{Conceptual Architecture}
\label{subsec:conceptual}

The architecture is organised into five conceptual layers, shown in Figure~\ref{fig:conceptual_arch}.

\textbf{Client Layer.} The SwiftTrack web portal and the driver mobile application communicate with the platform exclusively through the API Gateway over HTTP and WebSocket.

\textbf{API Gateway Layer.} A single Node.js proxy (port~8081) is the sole externally reachable component. It verifies a JWT on every non-public request, injects \texttt{x-username} and \texttt{x-role} headers into the forwarded request, and routes by URL prefix to the corresponding internal service.

\textbf{Application Service Layer.} Seven Node.js services implement business logic. Auth, Order, Items, Delivery, and Notify services expose HTTP endpoints accessible through the gateway. Payment and Route services have no HTTP interface and participate only through RabbitMQ.

\textbf{Message Broker Layer.} RabbitMQ~4 hosts a single durable topic exchange named \texttt{swift\_logistics}. All asynchronous inter-service communication passes through this exchange. Routing keys follow the pattern \texttt{<target>.<entity>.<action>} (e.g.\ \texttt{cms.order.create}, \texttt{order.wms.reserved}).

\textbf{Adapter and Legacy System Layer.} Three containers each co-host a mock legacy system and its adapter. The CMS Adapter bridges AMQP to SOAP, the ROS Adapter bridges AMQP to REST, and the WMS Adapter bridges AMQP to the proprietary TCP/IP protocol (simulated as intra-container HTTP). A shared PostgreSQL~16 instance persists data for the Auth, CMS, and Notify services.

Three communication paths operate in parallel. Synchronous HTTP requests travel from the client through the API Gateway to an application service, which returns an immediate acknowledgement. Asynchronous AMQP messages travel between application services and adapters via the exchange, with each adapter performing the necessary protocol translation before calling its legacy system. Real-time WebSocket frames travel from the Notify Service, through the API Gateway WebSocket proxy, to the connected client or driver.

\subsection{Implementation Architecture}
\label{subsec:implementation}

The full deployment is defined in \texttt{docker-compose.yml}. All thirteen containers share a single Docker bridge network named \texttt{internal}. Only two ports are forwarded to the host: \texttt{8081} (API Gateway, external-facing) and \texttt{15672} (RabbitMQ management UI, development convenience). Services that depend on RabbitMQ declare \texttt{depends\_on: condition: service\_healthy} so no container attempts an AMQP connection before the broker passes its health check (\texttt{rabbitmq-diagnostics ping}). PostgreSQL-dependent services wait similarly. Every container uses \texttt{restart: unless-stopped} for basic self-healing. Inter-service DNS uses the container names defined in the Compose file (e.g.\ \texttt{rabbitmq-service}, \texttt{postgres-service}). Credentials and secrets are injected via environment variables; \texttt{JWT\_SECRET} is shared between the API Gateway and Auth Service.

\subsection{Component Descriptions}
\label{subsec:components}

\subsubsection{Client Portal and Driver Mobile Application}

Neither client is implemented in the prototype; both are planned components. The web portal is a single-page application that communicates with the API Gateway over HTTP and maintains a WebSocket connection to \texttt{/notify} for real-time order status updates. The driver mobile application authenticates with the role \texttt{driver}, calls \texttt{POST /deliveries} to request a delivery manifest, and receives optimised route assignments via WebSocket push. Both clients authenticate via \texttt{POST /auth/login} and attach the issued JWT as an \texttt{Authorization: Bearer} header on all subsequent requests. Public routes (\texttt{/auth/signup}, \texttt{/auth/login}, \texttt{/health}) bypass JWT verification in the gateway.

\subsubsection{API Gateway}

Implemented in \texttt{source-code/services/api-gateway/index.js} using Node.js's built-in \texttt{http} module and the \texttt{http-proxy} library. It performs three functions: JWT authentication (\texttt{validateToken()} verifies the HS256 token and rejects invalid requests with HTTP~401); identity injection (the verified \texttt{username} and \texttt{role} claims are forwarded as \texttt{x-username} and \texttt{x-role} headers so downstream services need not re-verify the token); and routing (\texttt{resolveTarget()} maps URL prefix to internal service address: \texttt{/auth}~→~\texttt{auth-service:3000}, \texttt{/order}~→~\texttt{order-service:3000}, \texttt{/items}~→~\texttt{items-service:3000}, \texttt{/deliveries}~→~\texttt{delivery-service:3000}, \texttt{/notify}~→~\texttt{notify-service:3000}). WebSocket upgrades are proxied via the \texttt{upgrade} event handler.

\subsubsection{Auth Service}

Implemented in \texttt{source-code/services/auth-service/index.js} using Express.js, \texttt{bcryptjs}, \texttt{jsonwebtoken}, and \texttt{node-postgres}. It exposes four routes: \texttt{POST /signup}, \texttt{POST /login}, \texttt{POST /refresh}, and \texttt{POST /logout}. On login it issues a short-lived access token and a long-lived refresh token, both signed with HS256. Refresh tokens are stored in the \texttt{refresh\_tokens} table and deleted on logout, enabling server-side session revocation. Passwords are hashed with bcrypt at cost factor~10 and are never stored or logged in plain text.

\subsubsection{Order Service}

Implemented in \texttt{source-code/services/order-service/index.js} using Express.js via
\texttt{InternalRouter} and the shared \texttt{PubSub} client. It exposes three HTTP
endpoints (\texttt{POST /order}, \texttt{PATCH /order}, \texttt{GET /order}) and drives
the choreography-based Saga described in Section~\ref{sec:architectural_patterns}.
In-memory \texttt{Maps} (\texttt{pendingPayments}, \texttt{pendingDeliveryRequests}) hold
correlation state while awaiting asynchronous replies from downstream services. It
publishes to keys including \texttt{cms.order.create}, \texttt{payment.charge}, and
\texttt{wms.order.release}, and subscribes to the corresponding response keys such as
\texttt{order.payment.completed} and \texttt{order.wms.reserved}.

\subsubsection{Items Service}

Implemented in \texttt{source-code/services/items-service/index.js} using Express.js and PubSub. It exposes a single \texttt{GET /} endpoint. On each request it publishes \texttt{wms.items.request} with a \texttt{correlationId} and stores the ID in a pending-requests map. When the WMS Adapter replies on \texttt{wms.items.response}, the result is forwarded to the client via the Notify Service. Clients never call the WMS directly; all communication is mediated through the adapter layer.

\subsubsection{Delivery Service}

Implemented in \texttt{source-code/services/delivery-service/index.js} using Express.js and PubSub. \texttt{POST /} is called by a driver to request a delivery manifest: the service publishes \texttt{order.delivery.request\_next}, receives pending orders from the CMS Adapter, requests a route from the ROS Adapter via the Route Service, and pushes the result to the driver via a \texttt{notify.<driver>.delivery\_route\_assigned} event. \texttt{GET /} queries the WMS for current delivery status asynchronously. \texttt{PATCH /} marks a delivery as completed or failed, updates the WMS, and publishes a \texttt{notify.<clientId>.delivery\_update} event so the order owner is informed immediately.

\subsubsection{Payment Service}

Implemented in \texttt{source-code/services/payment-service/index.js} using PubSub only; it has no HTTP server. It subscribes to \texttt{order.created} to create a payment intent and notify the client. It subscribes to \texttt{payment.charge} to simulate processing: on success it publishes \texttt{order.payment.completed}; on failure it publishes \texttt{order.payment.failed}. The simulated success rate is approximately 90\%. In production this service would call a real payment processor.

\subsubsection{Route Service}

Implemented in \texttt{source-code/services/route-service/index.js} using PubSub only; it has no HTTP server. It maintains an in-memory \texttt{orderId}$\to$\texttt{location} index populated from \texttt{order.created} events. When it receives \texttt{route.delivery.path\_requested} from the Delivery Service, it assembles the list of stops, publishes \texttt{ros.delivery.optimize}, and when the ROS Adapter replies forwards the result as \texttt{delivery.route.path\_response}. Entries are removed from the index when orders leave the \texttt{pending\_delivery} state.

\subsubsection{Notify Service}

Implemented in \texttt{source-code/services/notify-service/index.js} using Node.js's \texttt{http} module, the \texttt{ws} WebSocket library, PubSub, and \texttt{node-postgres}. It maintains a \texttt{Map<userId, Set<WebSocket>>} of active connections and subscribes to all \texttt{notify.*} routing keys on a unique per-instance queue (\texttt{notifier.\$\{HOSTNAME\}}). When a notification arrives for a connected user it sends a JSON frame immediately. When the user is offline and \texttt{persist=1}, the notification is stored in the \texttt{pending\_notifications} table and flushed in timestamp order on the next WebSocket connection. The unique-queue design allows horizontal scale-out: each additional instance receives all notification events independently and serves its own connected users.

\subsubsection{CMS Service (Legacy + Adapter)}

The CMS container runs two processes: a mock SOAP server (\texttt{cms-service/index.js}) and the CMS Adapter (\texttt{cms-service/cms-adapter/index.js}). The SOAP server is described by \texttt{cms.wsdl} and implements four operations: \texttt{CreateOrder}, \texttt{UpdateOrderStatus}, \texttt{GetOrdersByUser}, and \texttt{GetNextPendingDelivery}. Orders are persisted to PostgreSQL with a JSONB \texttt{itemList} column. The CMS Adapter creates a typed SOAP client from the WSDL at startup using the \texttt{soap} library, subscribes to \texttt{cms.*} routing keys on the exchange, invokes the appropriate SOAP operation, and re-publishes the result on the reply key. The adapter reaches the SOAP server at \texttt{127.0.0.1:3000} within the same container.

\subsubsection{ROS Service (Legacy + Adapter)}

The ROS container runs a mock REST server (\texttt{ros-service/index.js}) and the ROS Adapter (\texttt{ros-service/ros-adapter/index.js}). The mock server exposes a single endpoint, \texttt{POST /api/ros/optimize-route}, which returns the provided locations array reordered as a dummy optimised sequence. The ROS Adapter subscribes to \texttt{ros.route.optimize} and \texttt{ros.delivery.optimize}, calls the REST endpoint via \texttt{axios}, and re-publishes the result on the corresponding reply key. Both components run in the same container; the adapter calls \texttt{127.0.0.1:3000} internally.

\subsubsection{WMS Service (Legacy + Adapter)}

The WMS container runs a mock REST server (\texttt{wms-service/index.js}) and the WMS Adapter (\texttt{wms-service/wms-adapter/index.js}). The mock server exposes five endpoints: \texttt{GET /api/wms/items}, \texttt{POST /api/wms/reserve}, \texttt{POST /api/wms/release}, \texttt{PATCH /api/wms/delivery-status}, and \texttt{GET /api/wms/delivery-status}. Inventory is held in-memory and resets when the container restarts. The WMS Adapter subscribes to \texttt{wms.items.request}, \texttt{order.confirmed}, \texttt{wms.order.release}, \texttt{wms.delivery.update\_status}, and \texttt{wms.delivery.status\_request}, calls the corresponding mock endpoints via \texttt{axios}, and re-publishes results on reply keys. The proprietary TCP/IP boundary is simulated by the intra-container HTTP call.

\subsubsection{Message Broker --- RabbitMQ}

The platform uses the \texttt{rabbitmq:4-management} Docker image. A single durable topic exchange named \texttt{swift\_logistics} is declared by the first service that connects. All queues are durable, ensuring messages survive broker restarts. The routing key convention is \texttt{<target>.<entity>.<action>} (e.g.\ \texttt{cms.order.create}, \texttt{order.wms.reserved}). The Notify Service uses unique per-instance queues (\texttt{notifier.\$\{HOSTNAME\}}) bound to \texttt{notify.*}; all other services use stable named queues. Connection and subscription management is centralised in \texttt{source-code/services/utility/pubsub.js}, which provides auto-reconnect with a five-second back-off and automatic subscriber re-registration on reconnect.

\subsubsection{Data Persistence --- PostgreSQL}

The platform uses a single \texttt{postgres:16-alpine} instance in the prototype. Three schema scripts in \texttt{source-code/db/} are executed automatically on first container start via the \texttt{/docker-entrypoint-initdb.d} mechanism: \texttt{auth.sql} creates the \texttt{users} and \texttt{refresh\_tokens} tables; \texttt{cms.sql} creates the \texttt{orders} table (with a JSONB \texttt{itemList} column); \texttt{notify.sql} creates the \texttt{pending\_notifications} table. All services access the database via the shared \texttt{db.js} connection pool utility using parameterised queries.

\subsection{Deployment Architecture}
\label{subsec:deployment}

All thirteen services are defined in a single \texttt{docker-compose.yml} at the repository root. Every service image extends \texttt{node:20-alpine}, providing a minimal and reproducible base. The database schema files in \texttt{source-code/db/} are mounted to the PostgreSQL container's \texttt{/docker-entrypoint-initdb.d} directory and applied automatically on first start.

Health-check ordering prevents startup race conditions. RabbitMQ declares a health check that runs \texttt{rabbitmq-diagnostics ping} at five-second intervals; all AMQP-dependent services wait for it to pass before starting. The entire platform is brought up with a single \texttt{docker compose up --build} command. Every container is configured with \texttt{restart: unless-stopped} so Docker automatically recovers individual failures without operator intervention.

For production, Docker Compose would be replaced by Kubernetes to support horizontal pod autoscaling on the Order, Notify, and Delivery services, rolling updates, a RabbitMQ cluster with mirrored queues, and per-service PostgreSQL instances.

\subsection{Rationale for Final Architecture}
\label{subsec:rationale}

The event-driven microservices architecture was selected over the two alternatives evaluated in Section~\ref{sec:alternatives} because it best satisfies the four most demanding requirements of the platform.

Heterogeneous integration is addressed by encapsulating each legacy protocol within a dedicated adapter container. The CMS SOAP contract, the ROS REST interface, and the WMS proprietary protocol are hidden behind an identical AMQP interface. Replacing any legacy system requires modifying only its adapter; all other services remain unchanged.

High-volume asynchronous processing is addressed by placing RabbitMQ durable queues between order submission and backend processing. The Order Service acknowledges the client immediately and publishes an event; CMS, WMS, Payment, and ROS adapters process from their own queues at their own pace. During peak load the queues act as a buffer, preventing back-pressure from reaching the client portal. Because consumer ACKs are sent only after successful processing, no message is lost if a consumer container restarts mid-operation.

Independent scalability is achieved because each of the thirteen containers is a separately deployable unit. In a Kubernetes deployment, Order, Notify, and Delivery services can be scaled out independently during peak hours.

The accepted trade-off is higher initial complexity: thirteen containers, distributed tracing across asynchronous flows, and eventual consistency rather than immediate consistency. This is mitigated by unifying on a single runtime (Node.js) and sharing utility modules (\texttt{pubsub.js}, \texttt{db.js}, \texttt{internalRouter.js}) across all services.
