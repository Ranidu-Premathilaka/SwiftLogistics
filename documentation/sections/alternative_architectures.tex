\section{Alternative Architectures}


\subsection{Alternative 1: Service-Oriented Architecture (SOA) with an Enterprise Service Bus}

\subsubsection{Overview}

In SOA with an ESB, the CMS, ROS, and WMS are each wrapped behind a standardised service interface, and all inter-service communication is mediated by an \textit{Enterprise Service Bus} (ESB). The ESB acts as the single integration hub, handling protocol translation, message routing, and orchestration between the client-facing layer and the back-end systems.

\subsubsection{Advantages}

\begin{itemize}
    \item All integration logic is centralised in the ESB, simplifying auditing, policy enforcement, and monitoring.
    \item Built-in connectors for SOAP, REST, JSON, and TCP reduce the need for custom adapter code.
    \item Distributed transaction coordination simplifies consistency across the CMS, ROS, and WMS.
\end{itemize}

\subsubsection{Disadvantages}

\begin{itemize}
    \item The ESB is in the critical path of every request, making any fault or overload an immediate platform-wide issue.
    \item ESB appliances scale vertically, making highthroughput peaks expensive and complex to handle.
    \item All integration changes must pass through the centralised bus, creating bottlenecks.
\end{itemize}

\subsubsection{Why Not Chosen}

The central ESB would become a performance bottleneck during high-volume order periods and cannot be independently scaled to meet the throughput demands of a growing logistics platform. The proposed event-driven architecture achieves the same integration goals while distributing load across independently scalable services.

\subsection{Alternative 2: Three-Tier Layered Architecture}
\label{subsec:alt2}

\subsubsection{Overview}

The three-tier layered architecture is one of the most widely adopted structural patterns where It organises a system into three horizontal layers with strict unidirectional dependencies: a \textit{presentation tier} that handles user interaction, a \textit{business logic tier} that processes requests and enforces domain rules, and a \textit{data tier} that manages persistent storage.

Applied to SwiftLogistics, this architecture would be realised as follows:

\begin{itemize}
    \item \textbf{Presentation tier:} The SwiftTrack web portal and the driver mobile application communicate directly with the application server over HTTPS.
    \item \textbf{Business logic tier:} A monolithic or modular application server (for example, a Node.js Express monolith) contains all business logic—order processing, route planning coordination, warehouse status management as well as adapter code that calls the CMS via SOAP, the ROS via REST, and the WMS via TCP/IP. All integration with the three back-end systems is handled synchronously within this tier, either using direct library calls or a shared internal service layer.
    \item \textbf{Data tier:} Centralised relational databases (e.g., PostgreSQL) store all application state: orders, user credentials, delivery status, and logs. The CMS, ROS, and WMS are accessed as external data sources from the business logic tier.
\end{itemize}

\subsubsection{Advantages}

\begin{itemize}
    \item Simplicity and rapid initial implementation
    \item Low operational overhead
    \item Low latency for synchronous flows
    \item Straightforward debugging
    \item Familiar deployment model
\end{itemize}

\subsubsection{Disadvantages}

\begin{itemize}
    \item Synchronous blocking on slow back-end calls stalls the entire order flow.
    \item Without a durable broker, a mid-transaction crash can silently drop orders with no replay mechanism.
    \item Scaling requires replicating the entire monolith, making fine-grained component-level scaling impractical.
    \item All adapter code lives in the same codebase, so changes to one back-end protocol risk regressions in others.
    \item Schema or logic changes require coordinated updates across the entire application, increasing release risk.
\end{itemize}

\subsubsection{Why Not Chosen}

The three-tier architecture was rejected primarily because synchronous, blocking integration is irreconcilable with SwiftLogistics' peak-load requirements and its zero-order-loss guarantee. During promotional sales periods, the system must process a large volume of incoming orders concurrently. A synchronous application server would queue all requests serially, with each request blocked on potentially slowcalls producing unacceptable response times and a high risk of request timeouts. Furthermore, without a durable message broker, the architecture provides no recovery mechanism for partial transaction failures thus The event-driven, microservices-based proposed architecture is selected to ensure these requirements are met.
