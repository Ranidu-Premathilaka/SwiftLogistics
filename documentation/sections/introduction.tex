\section{Introduction}
\label{sec:introduction}

% Overview of SwiftLogistics
\subsection{Background}
Swift Logistics (Pvt) Ltd. is a rapidly growing logistics company in Sri Lanka, specialising in last-mile delivery for e-commerce businesses. The company serves a diverse client base ranging from large online retailers to small-scale independent sellers, managing the complete last-mile delivery lifecycle from warehouse intake to doorstep delivery.

Despite its growth, Swift Logistics has historically operated with siloed, manual systems that function independently of one another. This fragmented approach has led to inefficiencies in order processing, limited visibility into delivery statuses, and an inability to scale operations during high-demand periods such as seasonal promotional events. To address these operational shortcomings and remain competitive in the growing Sri Lankan e-commerce market, Swift Logistics is replacing its legacy infrastructure with a modern, integrated platform branded as \textbf{SwiftTrack} — comprising a web-based client portal and a mobile application for delivery drivers.

\subsection{Problem Statement}
The central challenge in realising the SwiftTrack platform is the seamless integration of three critical backend systems that currently operate in isolation, each exposing a different interface and communication protocol:

\begin{itemize}
    \item \textbf{Client Management System (CMS):} A legacy, on-premise system responsible for managing client contracts, billing, and order intake. It exposes a SOAP-based XML API, representing an older integration paradigm.
    \item \textbf{Route Optimisation System (ROS):} A modern, cloud-based third-party service that accepts delivery addresses and vehicle availability data to compute optimal delivery routes. It provides a well-documented RESTful JSON API.
    \item \textbf{Warehouse Management System (WMS):} An internal system that tracks packages from the point of client receipt through to vehicle loading. It communicates via a proprietary messaging protocol over TCP/IP, offering real-time status updates.
\end{itemize}

The heterogeneous nature of these systems — differing in protocol (SOAP, REST, TCP/IP), data format (XML, JSON, binary), and deployment model (on-premise, cloud, internal) — demands a robust middleware layer capable of bridging these differences transparently. Additionally, the system must support high-volume asynchronous order processing, real-time tracking and notifications, distributed transaction consistency, and secure communication across all components.

\subsection{Objectives}
The primary objective of this project is to design and implement a middleware architecture that integrates the CMS, ROS, and WMS into a cohesive, reliable platform underpinning SwiftTrack. The specific objectives are:

\begin{itemize}
    \item \textbf{Heterogeneous Integration:} Provide transparent protocol and data format translation between the SOAP/XML CMS, the REST/JSON ROS, and the TCP/IP WMS.
    \item \textbf{Real-time Tracking and Notifications:} Enable immediate propagation of delivery status updates to the client portal and push route-change notifications to driver mobile apps.
    \item \textbf{High-Volume Asynchronous Processing:} Ensure the client portal remains responsive during peak order volumes by decoupling order submission from backend processing through asynchronous messaging.
    \item \textbf{Distributed Transaction Consistency:} Guarantee that a submitted order is consistently reflected across the CMS, WMS, and ROS, with defined recovery strategies for partial failures.
    \item \textbf{Scalability and Resilience:} Architect the system to scale horizontally and to tolerate the failure of any individual component without data loss or service interruption.
    \item \textbf{Security:} Enforce secure communication across all integration points, including TLS for transport, authenticated API access, and protection against common web vulnerabilities.
\end{itemize}

\subsection{Scope}
\textbf{In Scope:}
\begin{itemize}
    \item Design of the conceptual and implementation middleware architectures for integrating the CMS, ROS, and WMS.
    \item A functional prototype implementing mock services for the CMS, ROS, and WMS, demonstrating the end-to-end order submission flow and real-time status updates to a simple client UI.
    \item Architectural description and minimal implementation of the real-time tracking and notification system.
    \item Identification and justification of architectural and integration patterns used.
    \item Information security considerations applied during design and implementation.
\end{itemize}

\textbf{Out of Scope / Future Work:}
\begin{itemize}
    \item Full production-grade implementation of the CMS, ROS, and WMS (replaced by mocks in the prototype).
    \item Complete mobile application development for the driver app.
    \item Integration with actual third-party payment or billing gateways.
    \item Advanced analytics, reporting dashboards, and business intelligence features.
\end{itemize}

\textbf{Assumptions:}
\begin{itemize}
    \item All components of the solution are built exclusively using open-source technologies.
    \item The APIs and messaging interfaces of the three backend systems are as described in the assignment scenario.
    \item The prototype environment is a local development setup; production deployment considerations are discussed architecturally but not fully implemented.
\end{itemize}
