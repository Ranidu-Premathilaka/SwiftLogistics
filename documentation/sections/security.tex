\section{Information Security Considerations}
\label{sec:security}

This section covers security controls applied at design time and those implemented in the prototype. A clear distinction is made between controls that are operational and those deferred to a production deployment.

\subsection{Security Requirements}
\label{subsec:security_requirements}

The security goals for SwiftTrack are:
\begin{enumerate}
    \item All external client-to-backend communication must be authenticated.
    \item User credentials must be stored as one-way hashes.
    \item Internal services must not be directly reachable from outside the platform.
    \item The API must be resistant to common injection attacks.
\end{enumerate}

\subsection{Authentication and Authorisation}
\label{subsec:auth}

\subsubsection{JWT-Based User Authentication}

\textit{Status: Implemented.}

Upon login, the Auth Service validates the user's credentials against a stored password hash. On success, it issues a short-lived access token and a long-lived refresh token, both cryptographically signed. The refresh token is persisted for server-side revocation. The client attaches the access token to every subsequent request, and the API Gateway verifies it before forwarding to any internal service. Verified identity and role claims are propagated to downstream services via request headers, so no downstream service needs to re-verify the token.

Logout invalidates the refresh token server side, preventing it from being used to obtain new access tokens. 

\subsubsection{Role-Based Access Control}

\textit{Status: Partially implemented.}

Two roles are defined: client and driver. The role is set at registration, embedded in the token, and propagated by the gateway on each request towards the services. Protected endpoints enforce role checks and reject unauthorised callers.

\subsubsection{Service-to-Service Trust}

\textit{Status: Implemented via network isolation; mTLS not implemented.}

All inter-service traffic stays within a private internal container network. Services trust the identity and role headers injected by the gateway without re-verifying the token themselves. For production, mutual TLS via a service mesh would cryptographically authenticate each container-to-container call, preventing an attacker who compromises the internal network from impersonating a service.

\subsection{Data Protection}
\label{subsec:encryption}

\subsubsection{Password Storage}

\textit{Status: Implemented.}

Passwords are hashed using an adaptive, salted hashing algorithm before storage and are never logged. 

\subsubsection{Data in Transit}

\textit{Status: Designed and not implemented in prototype}

The prototype uses plain HTTP and WS. Production requires TLS terminated at the API Gateway (HTTPS for REST, WSS for WebSocket). Communication with the external ROS API must use HTTPS with API key authentication. Internal Docker bridge traffic does not require TLS because it is isolated from external network interfaces.

\subsubsection{Data at Rest}

\textit{Status: Designed and not implemented in prototype}

Sensitive data (credentials, orders, notifications) is stored in PostgreSQL with no encryption at rest in the prototype. Production would require filesystem or volume encryption on the database. Secrets would be managed by a dedicated secrets manager with automatic rotation rather than plain environment variables.

\subsection{Secrets Management}
\label{subsec:secrets}

\textit{Status: Basic (environment variables); production improvement required.}

Secrets such as signing keys and database credentials are injected as environment variables. Development defaults are provided for convenience but must never be used in production. Production requires a dedicated secrets manager with automatic rotation. Rotating the token signing key requires updating both the Auth Service and API Gateway simultaneously.

\subsection{Logging and Audit}
\label{subsec:security_monitoring}

\textit{Status: Minimal (stdout); centralised logging not implemented.}

All services write structured logs to stdout, captured by Docker. The Auth Service logs every authentication event and its outcome. The API Gateway logs every inbound request with method, URL, and target service. Production would require centralised log aggregation with automated alerts on repeated failures and elevated error rates.
