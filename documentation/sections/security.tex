\subsection{Authentication and Authorisation}
\label{subsec:auth}

\subsubsection{JWT-Based User Authentication}
%% GUIDE — STATUS: IMPLEMENTED
%%  Source: source-code/services/auth-service/index.js
%%          source-code/services/api-gateway/index.js
%%
%%  Flow:
%%  1. Client sends POST /auth/login { username, password }.
%%  2. Auth Service fetches bcrypt hash from PostgreSQL → compares with bcrypt.compare().
%%  3. On success: issues:
%%       accessToken  = jwt.sign({ username, role }, secret, { expiresIn: ... })
%%       refreshToken = jwt.sign({ username, role }, secret, { expiresIn: ... })
%%     Both signed with HMAC-SHA256 (HS256).
%%  4. refreshToken is persisted in refresh_tokens table; enables server-side revocation.
%%  5. Client attaches accessToken as "Authorization: Bearer <token>" on every request.
%%  6. API Gateway verifies token on every non-public route using
%%       jwt.verify(token, JWT_SECRET)
%%     and rejects with 401 if missing, malformed, or expired.
%%  7. Verified username and role are injected as x-username / x-role headers;
%%     no downstream service re-verifies the token.
%%
%%  Token revocation (logout): DELETE from refresh_tokens WHERE token = $1.
%%  This invalidates the refresh token; the short-lived access token is not
%%  revocable by design (accepted trade-off in prototype).

\subsection{Data Protection}
\label{subsec:encryption}

\subsubsection{Password Storage}
%% GUIDE — STATUS: IMPLEMENTED
%%  Source: source-code/services/auth-service/index.js (bcrypt.hash / bcrypt.compare)
%%  - bcryptjs used with cost factor 10 (≈100 ms hash time on a modern CPU).
%%  - Passwords are never stored or logged in plain text.
%%  - Adaptive work factor makes brute-force and rainbow-table attacks
%%    computationally impractical even if the PostgreSQL database is compromised.

\subsubsection{Data in Transit}
%% GUIDE — STATUS: DESIGNED, NOT IMPLEMENTED IN PROTOTYPE
%%  - The prototype runs over plain HTTP/WS (no TLS).
%%  - Design intention: TLS 1.2+ would be terminated at the API Gateway
%%    (HTTPS for the REST API, WSS for the WebSocket channel).
%%  - Communication with the third-party ROS API (external vendor) must use HTTPS;
%%    in the prototype the ROS service is a local container so plain HTTP suffices.
%%  - Internal Docker bridge communication does not require TLS because
%%    it is isolated from external network interfaces.

\subsubsection{Data at Rest}
%% GUIDE — STATUS: DESIGNED, NOT IMPLEMENTED IN PROTOTYPE
%%  - Sensitive data (user credentials, order details) stored in PostgreSQL.
%%  - Production recommendation: PostgreSQL Transparent Data Encryption (TDE)
%%    or filesystem-level encryption (e.g. LUKS) on the database volume.
%%  - JWT secrets and database credentials stored as environment variables
%%    in the prototype; production would use a dedicated secrets manager
%%    (HashiCorp Vault, Kubernetes Secrets with encryption-at-rest, or AWS Secrets Manager).

%% GUIDE — STATUS: IMPLEMENTED

%%  - All 13 containers share a single private Docker bridge network "internal".
