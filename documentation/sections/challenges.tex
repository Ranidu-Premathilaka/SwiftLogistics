\subsection{Challenge 2: Real-time Tracking and Notifications}
\label{subsec:challenge2}

\subsubsection{Problem Description}
%% GUIDE: 2-3 sentences.
%%  When a driver marks a package as delivered, the client portal must reflect
%%  the change immediately. Drivers must also receive push notifications for
%%  urgent route changes and new delivery assignments. Traditional HTTP polling
%%  is inefficient and introduces latency; a push-based approach is required.

\subsubsection{Solution Approach}
%% GUIDE:
%%  - Notify Service (notify-service/index.js) runs a WebSocket server using
%%    the ws library; each authenticated user's browser/app connects once and
%%    receives push frames.
%%  - Any service that needs to notify a user publishes a
%%    notify.<userId>.<event> routing key to the RabbitMQ exchange.
%%  - Notify Service subscribes to notify.* on a unique per-instance queue
%%    (notifier.\${HOSTNAME}) ensuring every instance receives every event.
%%  - For offline users: persist=1 messages are stored in pending_notifications
%%    (PostgreSQL) and flushed on the next WebSocket connection.
%%  Patterns: Publish-Subscribe, Event-Driven Architecture.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/realtime_solution.pdf}
    \caption{Real-time Tracking Solution Architecture}
    \label{fig:realtime_solution}
\end{figure}

\subsubsection{Implementation Details}
%% GUIDE:
%%  - When a driver marks delivery done: Delivery Service calls WMS Adapter
%%    (wms.delivery.update_status), receives confirmation, then publishes
%%    notify.<clientId>.delivery_update to the exchange.
%%  - Notify Service receives the event, looks up the clientId in its
%%    connection Map, and pushes { persist:1, payload: { event: delivery_update, ... } }.
%%  - If the client is offline the frame is stored in PostgreSQL and
%%    delivered on reconnection.
%%  - Route change notifications to drivers follow the same path:
%%    Route Service publishes notify.<driverUsername>.delivery_route_assigned
%%    after computing the optimised route via ROS.
%%  Source: notify-service/index.js, delivery-service/index.js, route-service/index.js.

\subsubsection{Benefits Achieved}
%% GUIDE:
%%  - Zero-polling architecture: no periodic HTTP requests; updates arrive
%%    within milliseconds of the triggering event.
%%  - Offline resilience: clients that disconnect do not miss notifications;
%%    the pending_notifications store ensures delivery on reconnect.
%%  - Horizontally scalable: each Notify Service instance has its own 
%%    queue bound to notify.*; all instances receive all events and serve
%%    their own connected users independently.

\subsection{Challenge 3: High-Volume, Asynchronous Processing}
\label{subsec:challenge3}

\subsubsection{Problem Description}
%% GUIDE: 2-3 sentences.
%%  During peak commercial events (Avurudu, Black Friday), the system must
%%  handle a surge in concurrent order submissions. Each order triggers
%%  multiple downstream operations (CMS, WMS, ROS, Payment) that may be slow.
%%  The client portal must remain responsive; it cannot block on these operations.

\subsubsection{Solution Approach}
%% GUIDE:
%%  - The RabbitMQ topic exchange acts as a durable buffer between order
%%    submission and backend processing.
%%  - Order Service publishes cms.order.create and immediately returns HTTP 200
%%    "Order creation initiated" to the client — no blocking.
%%  - CMS, WMS, Payment, and ROS adapters consume from their own durable queues
%%    at their own pace; if they are temporarily down, messages wait safely.
%%  - Competing Consumers: adding more adapter container instances allows the
%%    queue to be drained faster during peak load without any code changes.
%%  Patterns: Message Channel (durable queue), Competing Consumers, Event-Driven.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/async_processing.pdf}
    \caption{Asynchronous Processing Architecture}
    \label{fig:async_processing}
\end{figure}

\subsubsection{Implementation Details}
%% GUIDE:
%%  - PubSub utility (utility/pubsub.js): assertQueue with { durable: true }
%%    ensures messages survive a broker restart.
%%  - Manual consumer ACK (channel.ack(msg)) called only after the handler
%%    function completes successfully, so a consumer crash does not lose the message.
%%  - Auto-reconnect: if a service loses the AMQP connection, it retries every
%%    5 seconds and re-registers all subscribers on reconnect.
%%  - No message is lost even if the CMS adapter container crashes mid-processing:
%%    the message is re-queued and redelivered to the next available consumer.
%%  Source: utility/pubsub.js (connect, subscribe, #init methods).

\subsubsection{Benefits Achieved}
%% GUIDE:
%%  - Client portal is always responsive: the HTTP response is returned before
%%    any CMS, WMS, or ROS processing begins.
%%  - No orders are lost even if a backend service is temporarily unavailable;
%%    the durable queue holds the message until the service recovers.
%%  - Scale out: adding a second order-service container instance during
%%    peak load doubles throughput with no configuration change.

\subsection{Challenge 4: Transaction Management}
\label{subsec:challenge4}

\subsubsection{Problem Description}
%% GUIDE: 2-3 sentences.
%%  A single client order creates state in three independent systems:
%%  a record in the CMS, a stock reservation in the WMS, and a payment charge
%%  by the Payment Service. If any step fails after previous steps have
%%  succeeded, the system must roll back the completed steps to preserve
%%  consistency. Traditional distributed transaction protocols (2PC) are not
%%  practical in an asynchronous, event-driven architecture.

\subsubsection{Solution Approach}
%% GUIDE: Choreography-based Saga pattern.
%%  - Each service performs a local transaction and publishes an event.
%%  - The next service in the chain is triggered by that event.
%%  - On failure: the failing service publishes a compensating event that
%%    triggers rollback actions in already-completed services.
%%  - No central coordinator: the Order Service stashes contextual state
%%    (paymentToken, clientId) in in-memory Maps keyed by correlationId and
%%    reacts to reply events to advance or compensate the transaction.
%%  Patterns: Saga (choreography), Publish-Subscribe, Async RPC (correlationId).

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/transaction_management.pdf}
    \caption{Distributed Transaction Management with Saga Pattern}
    \label{fig:transaction_mgmt}
\end{figure}

\subsubsection{Implementation Details}
%% GUIDE: describe each saga step and its compensation:
%%
%%  SAGA STEPS (correlationId = x-request-id from client):
%%   1. POST /order           → cms.order.create              (Order Service)
%%   2. CMS CreateOrder SOAP  → order.created                 (CMS Adapter)
%%   3. payment_intent_created notification                    (Payment Service)
%%   4. PATCH /order          → cms.order.update_status       (Order Service)
%%   5. UpdateOrderStatus SOAP→ order.status_updated          (CMS Adapter)
%%   6. order.status_updated  → order.confirmed               (Order Service)
%%   7. WMS reserve           → order.wms.reserved            (WMS Adapter)
%%   8. payment.charge        → order.payment.completed       (Order Service → Payment)
%%
%%  COMPENSATION (payment failure):
%%   9b. order.payment.failed → wms.order.release             (Order Service)
%%   10b. WMS release reservation                              (WMS Adapter)
%%       + notify client of failure via notify.order.payment_failed
%%
%%  Key state tracking:
%%    pendingPayments Map (order-service/index.js): correlationId → { paymentToken, clientId }
%%    Populated on PATCH /order; consumed when order.wms.reserved arrives;
%%    used to retrieve paymentToken for payment.charge; cleared after payment.
%%
%%  Source: order-service/index.js (handleOrderStatusUpdated, handleWmsReserved,
%%          handleWmsReservationFailed, handlePaymentCompleted, handlePaymentFailed)
%%          payment-service/index.js, wms-adapter/index.js.

\subsubsection{Recovery Scenarios}
%% GUIDE: describe the four failure scenarios:
%%
%%  Scenario A — CMS Adapter fails before creating order:
%%    The cms.order.create message remains in the durable queue.
%%    When the CMS Adapter restarts, it picks up and processes the message.
%%    No compensation needed; no state was written to any system.
%%
%%  Scenario B — WMS Adapter fails after CMS confirms (order.confirmed published):
%%    The order.confirmed message is redelivered to the WMS Adapter on restart.
%%    WMS Adapter performs idempotent reserve (same orderId); duplicate protection
%%    handled by WMS internal logic.
%%
%%  Scenario C — Payment Service reports failure after WMS reserved:
%%    Order Service receives order.payment.failed and publishes wms.order.release.
%%    WMS Adapter releases the reservation. CMS order status remains at
%%    "order_confirmed"; the client is notified to retry payment.
%%
%%  Scenario D — Network partition (broker unreachable):
%%    All services auto-reconnect with 5-second back-off (PubSub.connect).
%%    In-flight correlations held in Order Service in-memory Maps may be lost on restart
%%    (known limitation; production fix: persist saga state to PostgreSQL).

\subsubsection{Benefits Achieved}
%% GUIDE:
%%  - No two-phase commit required; each local transaction is independent.
%%  - The system reaches eventual consistency across CMS, WMS, and Payment
%%    even when one service temporarily fails.
%%  - Compensating events provide a clean rollback path without distributed locks.

\subsection{Challenge 5: Scalability and Resilience}
\label{subsec:challenge5}

\subsubsection{Problem Description}
%% GUIDE: 2-3 sentences.
%%  The number of clients, drivers, and daily deliveries will grow as Swift
%%  Logistics expands. The architecture must scale horizontally without service
%%  interruption and must tolerate the failure of any single component without
%%  data loss.

\subsubsection{Solution Approach}
%% GUIDE:
%%  - Microservices: each of the 13 containers can be independently scaled.
%%  - Durable RabbitMQ queues provide a persistence buffer; messages are not
%%    lost if a consumer service restarts.
%%  - restart: unless-stopped on every container provides basic self-healing.
%%  - Notify Service unique-queue pattern allows horizontal fan-out scaling
%%    without re-engineering the notification delivery logic.
%%  - Docker Compose health checks ensure services only start when their
%%    dependencies (RabbitMQ, PostgreSQL) are actually ready.
%%  - Production path: Kubernetes with HPA, Rolling Updates, RabbitMQ cluster
%%    with mirrored queues for broker HA.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/scalability_resilience.pdf}
    \caption{Scalability and Resilience Architecture}
    \label{fig:scalability}
\end{figure}

\subsubsection{Implementation Details}
%% GUIDE (reference docker-compose.yml):
%%  - Health-check ordering: rabbitmq service uses rabbitmq-diagnostics ping;
%%    all RabbitMQ-dependent services set depends_on condition: service_healthy.
%%    This ensures no service attempts AMQP connection before the broker is ready.
%%  - Restart policy: restart: unless-stopped on every container.
%%    Docker automatically restarts a crashed container without manual intervention.
%%  - PubSub auto-reconnect (utility/pubsub.js): on connection close event,
%%    schedules reconnect after 5 seconds and re-binds all subscribers.
%%  - Notify Service per-instance queue: each scaled instance has its own
%%    unique queue (notifier.\${HOSTNAME}); adding a second instance immediately
%%    increases WebSocket delivery capacity without changing producer code.
%%  - Production note: Circuit Breaker pattern (e.g. opossum library) would
%%    prevent cascading failures when the CMS or WMS is slow to respond.

\subsubsection{Benefits Achieved}
%% GUIDE:
%%  - Any single container failure (including the CMS or WMS adapter) does not
%%    cause data loss; durable queues hold unprocessed messages.
%%  - The system self-heals via Docker's restart policy without operator intervention.
%%  - Each service scales independently; peak order processing capacity can be
%%    tripled by adding two more order-service containers with a single command.

\subsection{Challenge 6: Security}
\label{subsec:challenge6}

\subsubsection{Problem Description}
%% GUIDE: 2-3 sentences.
%%  Client-to-backend communication carries sensitive order data and user
%%  credentials. The third-party ROS API is accessed over the public internet.
%%  Internal services must not be accessible to external actors even if the
%%  API Gateway is bypassed.

\subsubsection{Solution Approach}
%% GUIDE:
%%  - Detailed coverage in Section~\ref{sec:security}; summarise here:
%%  - API Gateway Pattern: all external traffic enters through a single
%%    JWT-enforced entry point (port 8081); no internal service port is exposed.
%%  - JWT HS256 authentication with short-lived access tokens and long-lived
%%    refresh tokens stored server-side for revocation.
%%  - bcrypt password storage prevents credential exposure if the database is
%%    compromised.
%%  - Docker network isolation: all internal services on a private bridge
%%    network; only the API Gateway and RabbitMQ management UI are host-accessible.
%%  - Parameterised SQL queries protect against SQL injection.
%%  - Production additions: TLS 1.2+, rate limiting, CORS headers, mTLS.

\subsubsection{Benefits Achieved}
%% GUIDE:
%%  - A compromised client token cannot be used to call internal services directly.
%%  - Even if the database is stolen, bcrypt hashes make password recovery impractical.
%%  - The API Gateway acts as a choke point for access control, simplifying
%%    security auditing to a single service.
