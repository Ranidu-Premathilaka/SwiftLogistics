\section{Addressing Architectural Challenges}
\subsection{Overview}

Though most of these challenges are addressed and explained in the previous sections, this section will provide a consolidated view on how we have addressed these challenges in our architecture.

\subsection{Challenge 1: Heterogeneous Systems Integration}

\subsubsection{Solution}

Each legacy system is wrapped in a dedicated adapter container (the Adapter pattern, described in Section~\ref{subsec:integration_patterns}). The adapter is the only component that knows the native protocol of its system. All other services interact with the adapter exclusively through AMQP events. If a legacy system changes its interface, only its adapter needs to change.

\subsubsection{Benefits Achieved}

\begin{itemize}
    \item Protocol changes in any legacy system require modifying only its adapter container, leaving all other services unchanged.
    \item Adding a new integration (e.g.\ a GPS tracking service) requires only a new adapter to interface with the message broker with no changes to existing services.
\end{itemize} 

\subsection{Challenge 2: Real-time Tracking and Notifications}
\label{subsec:challenge2}

\subsubsection{Solution}

The Notify Service runs a WebSocket server and subscribes to all \texttt{notify.*} routing keys. Any service that needs to notify a user publishes to that with info such as the userid, payload, etc. While online users receive a the data immediately through the websocket offline users messages will be stored and delivered on reconnect(Only if the notification isn't time critial if so the message is dropped). By using this services can send out real-time updates when for example if a driver picks up an order to notify the according users by sending these events out.

\subsubsection{Benefits Achieved}

\begin{itemize}
    \item The architecture uses no polling, reducing both client and service-side handling overhead.
    \item Offline clients do not miss persistent notifications and ensures delivery on reconnect.
    \item The per-instance unique queue design allows the Notify Service to be scaled horizontally without any code change to message producers.
\end{itemize}

\subsection{Challenge 3: High-Volume, Asynchronous Processing}

\subsubsection{Solution}

Once a order submission or any high processing request is received the system will send a response to the client immediately and then the saga for that particular task will start using events through the message broker. Once the saga is completed either successfully or with a failure the system will send back the result through the webscocket to the client referencing its' idempotency key.

\subsubsection{Benefits Achieved}

\begin{itemize}
    \item The portal is always responsive, as responses are returned before any backend processing begins.
    \item The message broker's atleast once delivery guarantee ensures no event is lost during high loads where messages are queued until the system is ready to process them.
    \item The system can scale horizontally to handle increased load with no code changes.
\end{itemize}

\subsection{Challenge 4: Transaction Management}
\label{subsec:challenge4}

\subsubsection{Solution}

The choreography-based Saga pattern is used where each service performs a local transaction and publishes an event. The next service in the chain reacts to that event. On failure, the failing service publishes a compensating event that triggers rollback in already-completed services thus no central coordinator is required. These events are published with the same idempotency key allowing the entire transaction flow to be traced through with context. Examples of these transactions are listed in Section~\ref{subsec:user_stories}


\subsubsection{Benefits Achieved}

\begin{itemize}
    \item No two-phase commit or distributed lock is required.
    \item The system reaches eventual consistency across CMS, WMS, and Payment even when one service temporarily fails.
    \item Compensating events provide a clean rollback path that is verifiable by inspecting routing key sequences.
\end{itemize}

\subsection{Challenge 5: Scalability and Resilience}
\label{subsec:challenge5}

\subsubsection{Solution}

Each of the containers is independently deployable and scalable horizontally. Durable RabbitMQ queues buffer messages when a consumer is temporarily unavailable. For production, Kubernetes would provide automatic scale-out based on queue depth or CPU usage.

\subsubsection{Benefits Achieved}

\begin{itemize}
    \item A single container failure does not cause data loss because durable queues hold unprocessed messages until the container restarts.
    \item The \texttt{restart: unless-stopped} policy provides automatic recovery without operator intervention.
    \item Each service scales independently, so peak order processing capacity can be increased without affecting Auth or Payment services.
\end{itemize}

\subsection{Challenge 6: Security}
\label{subsec:challenge6}

\subsubsection{Solution}

The API Gateway enforces all requests to go through it where it only exposes the nessassary services to outside. There JWT verification is done at the gateway level making sure that only authorized users are allowed in the system. the /auth endpoint is allowed without token verification where it's the sole service that handles user registration and login. Security design is explained in more detail in Section~\ref{sec:security}.

\subsubsection{Benefits Achieved}

\begin{itemize}
    \item A compromised client token cannot be used to call internal services directly because no internal port is reachable from outside.
    \item Centralising authentication at the API Gateway reduces the security audit surface to a single service.
\end{itemize}
