\section{Architectural and Integration Patterns}
\subsection{Architectural Patterns}

\subsubsection{Microservices Architecture}

Each business capability is deployed as an independently runnable and scalable container. The thirteen containers are grouped by role: client-facing services (Auth, Order, Items, Delivery, Notify), backend processors (Payment, Route), legacy adapters (CMS, ROS, WMS), and infrastructure (RabbitMQ, PostgreSQL). Each container has a single responsibility, allowing individual services to be redeployed or scaled without affecting the rest of the system.

\subsubsection{Event-Driven Architecture}

Services communicate by publishing and consuming events rather than making direct synchronous calls to each other. For example every state change in the order lifecycle is expressed as a routing key published as \texttt{order.confirmed}, \texttt{order.wms.reserved}, \texttt{order.payment.completed}, and others. Producers have no knowledge of their consumers. Adding a new service that must react to an existing event requires only a new queue binding, with no change to any existing service. 

\subsubsection{API Gateway Pattern}

API gateway is used to handle three types of tasks each being, JWT token validation, identity propagation towards services and most importantly routing. It also acts as a WebSocket proxy for the Notify Service. By doing this backend processing internal services are not exposed to the outside world.

\subsubsection{Service Descovery Pattern}

Here we've taken utilization of docker's internal DNS for service discovery. Each service is registered with a stable hostname (e.g.\ \texttt{order-service}) and the API Gateway routes requests to these hostnames. By doing this on scenarios where multiple instances of the services are running, the internal docker DNS will automatically load balance requests according to round-robin. 

\subsection{Integration Patterns}
\label{subsec:integration_patterns}

\subsubsection{Pub-Sub Pattern}

RabbitMQ is used as the message channel backbone. Two types of channels are in use: point-to-point channels, where routing keys follow a \texttt{receiver.sender.event} convention and each message is consumed by exactly one service, and state-change event channels, where routing keys such as \texttt{order.created} broadcast lifecycle events to any interested subscriber.


\subsubsection{Adapter Pattern}

Each legacy integration adapter (CMS, ROS, WMS) listens for events published on the message bus and translates them into the native protocol of its target system. This shields the rest of the platform from each system's specific interface, whether SOAP, REST, or TCP, presenting a uniform event-driven interface to all other services regardless of the underlying protocol.

\subsubsection{Saga Pattern}

The system implements two choreography-based sagas: an order creation saga, which coordinates the CMS, WMS, and Payment services across the order lifecycle, and a delivery completion saga, which coordinates the WMS and Notify services when a driver marks an order as delivered. Each saga is driven entirely by events, with no central orchestrator. \subsubsection{Circuit Breaker Pattern}

Each saga step includes a circuit breaker mechanism. If a service fails to respond within a configured timeout, the circuit breaker opens, preventing further attempts to call that service and preventing the start of that saga. A health check is done periodially to monitor if if the service is back alive closing back the circuit through event based publishing. Currently this implementation isn't reflected with the prototype but it is a critical part of the final implementation to ensure system resilience under failure conditions.
