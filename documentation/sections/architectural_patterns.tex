\subsubsection{Event-Driven Architecture}
%% GUIDE — STATUS: IMPLEMENTED
%%  - Describe: services communicate by publishing and consuming events rather
%%    than making direct synchronous calls.
%%  - In SwiftLogistics: every state change in the order lifecycle is represented
%%    as an event published to the "swift_logistics" topic exchange:
%%      order created → order.created
%%      order confirmed → order.status_updated → order.confirmed

%%  - Benefits: producers and consumers are fully decoupled; CMS adapter

\subsubsection{API Gateway Pattern}
%% GUIDE — STATUS: IMPLEMENTED
%%  - Describe: a single entry point that handles cross-cutting concerns before
%%    routing to internal services.

%%      · Authentication: validateToken() verifies HS256 JWT and throws 401 early.

\subsubsection{Message Channel}
%% GUIDE — STATUS: IMPLEMENTED
%%  - In SwiftLogistics: RabbitMQ queues are the message channels.
%%  - All queues are durable (survive broker restart).
%%  - Two channel types in use:
%%      Point-to-point: each service has a stable, named queue
%%        (e.g. "order-service-queue.cms.order.create"). Only one instance
%%        (or competing group) consumes from each queue.
%%      Pub-Sub fanout: Notify Service creates a unique per-instance queue
%%        (notifier.${HOSTNAME}) bound to notify.* patterns, so every
%%        running instance receives all notification events.

\subsubsection{Message Translator}
%% GUIDE — STATUS: IMPLEMENTED
%%  - In SwiftLogistics each adapter is a Message Translator:
%%     · CMS Adapter: receives canonical JSON (correlationId, clientId, orderData)

\subsubsection{Content-Based Router}
%% GUIDE — STATUS: IMPLEMENTED (via RabbitMQ topic exchange)
%%  - RabbitMQ's topic exchange acts as the content-based router: the routing key
%%    on each published message determines which queue(s) receive it.
%%  - Example: when Order Service publishes order.confirmed, only the WMS Adapter
%%    queue (bound to "order.confirmed") receives it — CMS and ROS adapters are
%%    not notified, even though they are all connected to the same exchange.
%%  - Example: notify.* routing key pattern means all notify.order.* and
%%    notify.client.* events land in the Notify Service queue(s).

\subsubsection{Request-Reply (Async RPC) Pattern}
%% GUIDE — STATUS: IMPLEMENTED
%%  - Used wherever a service needs a response from a legacy system but must
%%    remain non-blocking.
%%  - In SwiftLogistics:
%%     · Items Service (items-service/index.js): publishes wms.items.request with
%%       a correlationId, stores the correlationId in pendingItemRequests Map,
%%       then uses Notify Service to push the response when wms.items.response
%%       arrives.
%%     · Order Service: similar pattern for order creation (publishes cms.order.create
%%       with correlationId; awaits order.created reply keyed by correlationId).
%%  - Correlation IDs are generated from the x-request-id idempotency header sent
%%    by the client, ensuring exactly-once processing for duplicate requests.

\subsubsection{Publish-Subscribe Pattern}
%% GUIDE — STATUS: IMPLEMENTED
%%  - Used for broadcasting events to multiple independent consumers.
%%  - In SwiftLogistics: every event published to the "swift_logistics" topic
%%    exchange is automatically routed to ALL queues whose binding key matches
%%    the routing key.
%%  - Key example: order.confirmed is consumed by BOTH the WMS Adapter (to
%%    reserve stock) and potentially the Route Service — producers need not know
%%    the list of consumers.
%%  - Notify Service pub-sub is the primary real-time delivery mechanism: any
%%    service publishes notify.<userId>.<event> and the Notify Service pushes
%%    it over WebSocket to the connected user.
%%  - Source: PubSub.subscribe() in utility/pubsub.js.

\subsubsection{Competing Consumers}
%% GUIDE — STATUS: ARCHITECTURALLY SUPPORTED (single instance in prototype)
%%  - Describe: multiple consumer instances share a single durable queue;
%%    RabbitMQ delivers each message to exactly one consumer (round-robin).
%%  - In SwiftLogistics: the prototype runs one instance per service, but the
%%    design supports horizontal scaling. Adding a second order-service container
%%    means both instances share "order-service-queue.*" queues; each message
%%    is processed by exactly one instance — no double-processing.
%%  - Exception: Notify Service uses unique per-instance queues so ALL instances
%%    receive ALL notification events (fanout, not competing consumer).

\subsubsection{Dead Letter Channel}
%% GUIDE — STATUS: ARCHITECTURALLY DESCRIBED, NOT IMPLEMENTED IN PROTOTYPE
%%  - Describe: messages that cannot be processed (e.g. persistent SOAP errors,
%%    repeatedly nacked messages) are routed to a separate Dead Letter Exchange
%%    for inspection and retry.
%%  - What should happen in production:
%%     · Configure x-dead-letter-exchange and x-message-ttl on each adapter queue.
%%     · Failed processing: adapter catches exception and nacks without requeue,
%%       causing RabbitMQ to reroute to the DLX.
%%     · A separate DLQ consumer logs the failure, alerts ops, and retries later.
%%  - Current prototype: on exception, adapters log the error and drop the message

\subsubsection{Saga Pattern (Choreography)}
%% GUIDE — STATUS: IMPLEMENTED
%%  - Describe: a distributed transaction is implemented as a sequence of local
%%    transactions, each publishing an event that triggers the next step. No
%%    central orchestrator; each service reacts to events and emits new events
%%    or compensating events.
%%  - Order creation saga in SwiftLogistics (correlationId links all steps):
%%
%%     Step 1:  Client → POST /order
%%              Order Service publishes  cms.order.create
%%     Step 2:  CMS Adapter processes → publishes  order.created
%%     Step 3:  Payment Service receives order.created →
%%              creates payment intent → publishes notify.order.payment_intent_created
%%     Step 4:  Client confirms → PATCH /order {status: order_confirmed, paymentToken}
%%              Order Service publishes  cms.order.update_status
%%     Step 5:  CMS Adapter updates → publishes  order.status_updated
%%     Step 6:  Order Service receives order.status_updated →
%%              publishes  order.confirmed
%%     Step 7:  WMS Adapter reserves stock → publishes  order.wms.reserved
%%     Step 8:  Order Service receives order.wms.reserved →
%%              publishes  payment.charge  (using stashed paymentToken)
%%     Step 9a: Payment succeeds → publishes order.payment.completed →
%%              Order Service notifies client
%%     Step 9b: Payment fails   → publishes order.payment.failed →
%%              Order Service publishes wms.order.release  (COMPENSATION)
%%              WMS Adapter releases reservation (saga rollback)
%%  - Source: order-service/index.js (pendingPayments Map tracks correlationId)
%%            payment-service/index.js, wms-adapter/index.js.

\subsection{Rationale for Pattern Selection}
\label{subsec:pattern_rationale}

%% GUIDE — List each architectural challenge from §\ref{sec:introduction}
%%   and state which pattern(s) address it, with a one-sentence justification.
%%
%%   Challenge 1 – Heterogeneous Integration:
%%     Message Translator pattern (CMS/ROS/WMS adapters) — isolates protocol
%%     and data-format conversion within a single component per system.
%%
%%   Challenge 2 – Real-time Tracking:
%%     Publish-Subscribe + Event-Driven Architecture — Notify Service subscribes
%%     to all notify.* events and pushes over WebSocket without polling.
%%
%%   Challenge 3 – High-Volume Async Processing:
%%     Message Channel (durable queues) + Competing Consumers —
%%     orders are buffered in the queue during traffic spikes; multiple
%%     consumer instances drain the queue without degrading the portal response.
%%
%%   Challenge 4 – Transaction Management:
%%     Saga Pattern (choreography) + Async RPC (correlationId) — each step
%%     of the distributed order transaction is an independent local operation
%%     with a compensating event for rollback.
%%
%%   Challenge 5 – Scalability and Resilience:
%%     Microservices Architecture + Competing Consumers — each service scales
%%     independently; RabbitMQ durable queues act as the buffer that prevents
%%     data loss when a consumer service restarts.
%%
%%   Challenge 6 – Security:
%%     API Gateway Pattern — single enforcement point for JWT verification;
%%     no internal service is directly reachable from outside the Docker network.
